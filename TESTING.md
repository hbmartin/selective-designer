# Testing Strategy

This project uses a layered test system. The default rule is to verify behavior at the cheapest layer that proves the contract, then add a higher layer only when the behavior crosses process, browser, persistence, or routing boundaries.

## Layer Map

| Layer | File pattern | Command | Contract |
| --- | --- | --- | --- |
| Property tests | `tests/unit/**/*.unit.spec.ts` using `@tests/support/property-testing` | `pnpm test:property` | Invariants over generated inputs for pure functions, state transitions, validators, and data mappers. |
| Unit tests | `tests/unit/**/*.unit.{test,spec}.{ts,tsx}` | `pnpm test:unit` | Business logic in isolation. Mock only true I/O boundaries such as DB, network, provider SDKs, clock, and generated IDs. |
| Browser component tests | `tests/browser/**/*.browser.{test,spec}.tsx` | `pnpm test:browser` | Component rendering and user interactions in Chromium through Vitest Browser. |
| Public workflow integration tests | `tests/integration/**/*.workflow.integration.test.{ts,tsx,mts,cts,js,jsx,mjs,cjs}` | `pnpm test:integration:workflow` | Sub-feature workflows through module public APIs only. No module-internal imports. Assert observable outputs and fake or real port side effects. |
| Adapter integration tests | Ordinary owner-specific `*.integration.test.*` specs under `tests/integration` | `pnpm test:integration <ordinary-file>` | Repository, webhook, SDK, and provider adapters against realistic local infrastructure such as PGlite. The `test:integration:adapters` alias selects only `infrastructure/__tests__` paths. |
| Native PostgreSQL integration | PostgreSQL-marked `*.postgres.integration.test.*` specs under `tests/integration` | `pnpm test:integration:postgres` (optionally `<postgres-file>`) | Real PostgreSQL migration, transaction, locking, and driver contracts using disposable Docker/Testcontainers databases. |
| E2E UI tests | `tests/e2e/*.spec.ts` | `pnpm test:e2e` or `pnpm test:e2e:chromium` | User-facing journeys from UI to rendered outcome. Assert durable side effects when the workflow writes data. |
| Visual regression | `tests/e2e/visual/*.visual.spec.ts` | `pnpm test:e2e:visual` | Stable critical screens with local Playwright snapshots. Baseline updates use `pnpm test:e2e:visual:update` and require review. |
| Coverage | Ordinary Vitest projects | `pnpm test:coverage` | Floor metric for touched code and trend signal in CI. Do not treat line coverage as proof of assertion quality. |
| Mutation testing | Stryker scoped configs | `pnpm test:mutation:critical` or scoped scripts | Test sensitivity for critical domain/application logic. Run periodically and for risky auth, authorization, and data-loss changes. |

`pnpm test` runs the full ordinary Vitest suite: unit, browser, architecture/security, and PGLite integration projects. Dedicated PostgreSQL tests use `pnpm test:integration:postgres` (Docker required); Playwright tests use `pnpm test:e2e`. Use the layer commands when you need a faster or more diagnostic signal. Focus ordinary specs with `pnpm test:integration <ordinary-file>` and native PostgreSQL specs with `pnpm test:integration:postgres <postgres-file>`; the ordinary command excludes PostgreSQL-marked specs.

## Fixture tooling and discovery

Integration discovery, PostgreSQL exclusion/inclusion, and the integration naming/workflow-import checks support exactly `ts`, `tsx`, `mts`, `cts`, `js`, `jsx`, `mjs`, and `cjs` extensions. Integration files retain the `.integration.test` suffix before the extension. Unit and browser project membership is unchanged; property-placement checks cover both `.unit.spec` and `.unit.test` using the existing unit-extension family.

Workflow reporter fixtures require the project-pinned pnpm to be available through the caller's PATH. They use the first PATH candidate, verify its exact version, and bind execution to that executable. A mismatched raw pnpm fails instead of automatically switching versions. An already-cached Corepack pnpm shim on PATH may work offline; a bare `corepack pnpm` launch without a PATH pnpm is not a fallback. Fixtures neither use `npm_execpath` nor download tools or repair dependencies.

For direct Vitest or IDE launches, expose the already-installed pinned pnpm with a command-scoped PATH or equivalent IDE runner environment:

```bash
PATH="/absolute/path/to/pinned-pnpm/bin:$PATH" node node_modules/vitest/vitest.mjs run --project=unit tests/security/test-workflow.unit.spec.ts
```

Fixture execution requires POSIX hosts providing `/bin/bash`, `/bin/ps`, and `/bin/sh`; the process inspection used here is supported on macOS and the Ubuntu CI runners.

Git configuration, ignore/attribute sources, and private executable shims belong to fixture-owned support directories outside their Git worktrees. Fixture commands use the current test Node through that private bin. Fixture-owned `node_modules/.bin` directories must not contain `node` or `pnpm`; collisions fail at every raw and shell launch, including version probing and entries added after environment creation. All command working directories must be the owned fixture root or descendants (including support); symlink traversal and external working directories are rejected. Missing owned paths remain missing and produce the normal spawn error. The `node_modules` and `.bin` containers themselves must be owned directories; linked individual dependencies are not traversed.

Fixture commands start a trusted current-Node supervisor through private, versioned IPC. It captures its own original process identity before permission to launch the requested workload, then synchronously captures the workload's birth identity. Arguments and environment are snapshotted before startup; enumerable inherited environment entries are preserved, own entries shadow inherited entries, and undefined values are omitted. The requested executable spelling and working directory remain intact; native startup errors such as `ENOENT` are reported separately. Supervisor startup uses a sanitized environment and an existing fixture cwd, so target settings cannot run before the ownership gate. Execution timeouts include startup.

Supervisor and workload identities have different roles. The supervisor remains a group anchor after workload exit and through TERM cleanup; only the original live workload can authorize new detached-group registration. Registration checks live ownership immediately and waits only for an ancestor command's pending startup, never unrelated startups. When a valid snapshot shows that only the supervisor remains and the workload has exited or failed to spawn, private retirement avoids an unnecessary two-second wait without suppressing TERM for detached groups. IPC transport failures remain diagnostic and permit fresh inspection; inspection failures still stop the attempt. `CommandResult.terminationSource` labels actual workload results and observed supervisor-signal fallback. Missing-workload errors are finalized after reconciliation so buffered workload reports can arrive before settlement. A known workload result is never overwritten by subsequent supervisor termination or late IPC. A confirmed spawn failure clears provisional supervisor termination fields because no workload terminated. Unexpected supervisor exits retain their missing-workload diagnostic alongside subsequent cleanup failures; exits caused by cleanup already in progress do not introduce that diagnostic.

Each command owns its process group until a fresh snapshot confirms retirement. Deliberately detached descendants must register through `registerFixtureProcessGroup(fixture, pid)` while their originating workload is live; registration closes synchronously when cleanup starts. The test-only `captureFixtureProcessGroup` alternative returns an exact scoped cleanup capability. Scenario safety scopes and unique handshake/observation directories exist before launch or readiness awaits. Readiness files never authorize signaling; arbitrary unregistered daemon containment is unsupported.

A leaderless group requires continuity through a member identity retained from its last authenticated snapshot. Unseen members cannot establish authority when every witness disappears. Such ambiguity retains the fixture and remains unsignaled, even if the remaining processes might be original descendants. Empty groups and positively replaced original leaders can be retired from fresh evidence. Exact `ps` start strings have finite precision, and inspection plus signaling is not atomic: this is portable observational cleanup, not race-free OS containment. No time tolerances are added.

Teardown uses one absolute budget: a two-second termination phase and one-second final confirmation/output-drain phase. Any failed or malformed global inspection stops that attempt immediately; valid snapshots allow independent verified groups to proceed when another group's identity is uncertain. A pass that stops on inspection or identity failure requires a later explicit disposal to recover. Recovery during output draining joins active group work and uses the remaining original deadline without restarting grace. A later attempt after settlement gets a fresh bounded recovery budget.

Concurrent cleanup shares inspection and signaling but publishes an outcome for each group. A scoped capability observes only its requested group's outcome; fixture-wide disposal aggregates all groups. A command joining an existing pass stops waiting at its own original deadline without shortening the shared pass. Pending groups leave explicit `owned-groups-unconfirmed` tokens and retain their pass locks, so later disposal joins without duplicate signals. Fresh retirement evidence reconciles those group tokens; output-drain tokens retain their separate acknowledgement rules. Fixture-wide disposal joins all active passes, including passes installed during command cleanup, before final reconciliation. This join does not authorize automatic retries or reset grace periods. Reconciled group failures no longer fail disposal; unrelated orchestration errors still propagate. Equivalent caller/pass deadline failures publish one token per exact group and pass; different failures and recovery passes remain distinct.

Every present pipe is checked for EOF on every completion path. A prematurely closed or destroyed pipe leaves its own sticky `output-drain-unconfirmed` token, even if child `close` arrives normally. Results retain readonly `cleanupFailures` and historical errors after recovery. `unresolvedFixtureCleanupFailures(fixture, tokens)` queries only those exact tokens still unresolved; scenario success does not depend on historical errors or sibling scopes. After known groups are freshly verified stopped, `acknowledgeFixtureCleanupFailure(fixture, token, { reason })` accepts only that fixture's exact unresolved output token and a nonempty reason. It never signals a process.

`disposeFixtureCommands` closes the fixture to new work and registrations. Disposal recovers eligible recorded group failures before waiting for output, joins concurrent passes, and retains the root if any obligation remains. Failed passes remain retryable. Retained supervisor handles and IPC endpoints are unreferenced after command settlement and released after verified retirement; late events cannot rewrite returned results. Collection teardown attempts every fixture, aggregates failures, and restores test state in `finally`. Scoped Semgrep and recursive, syntax-only architecture checks centralize direct, captured, and destructured signaling and require persistent replacements for synthetic `process.kill` spies. Discovery covers executable TypeScript/JavaScript extensions, excludes declaration files, and does not follow symlinks.

The project Semgrep ignore list enables fixture support and security sources in normal scans while leaving other test directories, including integration tests, excluded. The three integration-only rules for awaited loader assertions, PGlite setup placement, and optional cleanup remain deferred; the layering checker currently enforces naming, workflow-import, and property-placement policy rather than those three checks.

## Functional Correctness

Property tests should target invariants that are easy to state and expensive to enumerate manually:

- Normalizers are idempotent and preserve the expected semantic value.
- Validators accept all generated valid values and reject generated invalid families.
- Authorization and policy predicates match their truth table for generated users, roles, and targets.
- Data mappers round-trip, preserve IDs, and do not leak provider-only fields.
- Pagination, cursor, and search helpers keep ordering and limits stable.

Use `PROPERTY_DEFAULTS` from `tests/support/property-testing.ts` so generated tests are reproducible locally and in CI. Prefer bounded generators over broad arbitrary objects; failures should shrink to useful examples.

Unit tests should cover the business rule directly from `tests/unit`. Fakes are preferred over mocks when they make the observable behavior clearer. Mock only I/O boundaries, time, generated IDs, or provider APIs.

## Integration

There are two intentional integration shapes:

- Public workflow integration tests exercise a module through `index.ts`, `server.ts`, `client.ts`, `presentation.ts`, or a test-only `testing.ts` gate when internals are intentionally part of the test setup. They are for sub-feature workflows and should not import `domain/`, `application/`, `infrastructure/`, `transport/`, or `factory.ts` directly. `pnpm check:test-layering` enforces the existing workflow import-gate policy across the integration extensions documented above. The checker currently permits exactly `index`, `server`, `client`, and `presentation` module gates (with the existing kernel exception); the `testing` gate described by the architecture is not yet accepted by this workflow checker. Broader import-gate policy alignment is separate work. Ordinary public workflows use `*.workflow.integration.test.<extension>`; dedicated PostgreSQL workflows use `*.workflow.postgres.integration.test.<extension>`. The reversed `.postgres.workflow` spelling is rejected.
- Adapter integration tests live under `tests/integration` and may use owner `testing.ts` gates for the adapter internals they are proving. These tests assert on durable behavior: DB rows, emitted events, provider payloads, idempotency, pagination, and transaction effects.

Use PGlite for fast repository and module-level checks. For repository SQL or persistence behavior, raw SQL, schema serialization, migrations, database clients/drivers, or transaction/locking changes, also run `pnpm test:integration:postgres` (Docker required). Add or extend PostgreSQL coverage when PGlite cannot prove the contract. The dedicated suite runs its own `*.postgres.integration.test.*` specs; it does not repeat every ordinary repository test. Provider/webhook-only changes use focused adapter checks unless persistence is also affected. Use appropriate local infrastructure or Docker/Testcontainers for object-storage, queue, extension, or network contracts that PGlite cannot represent.

## End To End

Local and CI browser/visual tests use disposable in-memory PGlite on the shared endpoint declared by the E2E database configuration. Playwright config passes the same connection to workers and webserver startup, overriding runtime and migration database bindings. The webserver alone runs migrations and seeding; do not prepare a separate Docker database or use `db:push` in these jobs. Keep one worker and `reuseExistingServer: false`. MinIO remains required for storage flows, and dedicated PostgreSQL integration tests remain the native database gate.

The signaling corpus is inert JSON. `pnpm semgrep:fixtures` copies the real rule configuration into a disposable scope and parses the examples with Semgrep; it never executes them. `pnpm check` and Semgrep CI run these engine regressions alongside the TypeScript syntax guard.

E2E tests are for user-facing confidence, not for exhaustive branch coverage. Add or update E2E tests when a change touches routing, auth/session behavior, persistence from the UI, upload/download flows, or cross-module workflows that users depend on.

E2E assertions should use user-visible locators first, then verify the next rendered state. For write paths, also verify the durable side effect through a declared service contract, seeded database state, or test helper. Prepare state outside the UI unless the UI path itself is the behavior under test.

Visual tests should stay focused on stable critical screens. Do not approve snapshot changes without reviewing the rendered difference and the reason for the change.

## Quality Gates

Local development and agent work should usually run:

```bash
pnpm format:changed
pnpm check
pnpm test              # Full ordinary Vitest suite
```

`pnpm test:affected` remains a compatibility alias for `pnpm test`. It runs the full ordinary suite even with a clean working tree. Full-suite execution avoids missed tests from implicit setup dependencies, mock aliases, imported assets, and deleted files; dependency-cruiser remains an architecture check rather than a test selector.

`pnpm test:affected:list` uses native `vitest list --filesOnly` discovery and lists all ordinary test files as `[project] path` lines. Add `--json` for Vitest's array of objects with `file` (absolute path) and `projectName`. The previous selector's `--base`, `--summary`, custom `--verbose` behavior, and selection-report JSON are retired. Explicit Vitest filters remain available through the native commands.

The Coverage CI job runs the full ordinary suite, and the PostgreSQL Integration job runs the dedicated suite. There are no per-change PostgreSQL impact predictions. Neither `pnpm verify` nor `pnpm verify:task` automatically runs PostgreSQL tests; use the escalation rules below and retain `pnpm check:migrations` for schema or migration edits.

CodeQL is intentionally opt-in locally because the CLI is not a Node dependency. Use `pnpm codeql:test`, `pnpm codeql:db`, and `pnpm codeql:analyze` when changing `.github/codeql/**` or when investigating semantic security/data-flow behavior. These commands call the CodeQL CLI directly, install the local query pack dependencies first, and write outputs under `test-results/codeql/`.

Escalate based on touched surface:

| Change touches | Add |
| --- | --- |
| Pure domain policies, validators, or mappers | `pnpm test:property` and `pnpm test:unit` |
| Shared React components or forms | `pnpm test:browser` and browser inspection when layout changes |
| Repository SQL/persistence, schema serialization, migrations, drivers, transactions, locking | `pnpm test:integration <ordinary-file>` and `pnpm test:integration:postgres`; also `pnpm check:migrations` for schema/migration edits |
| Provider or webhook contracts without persistence changes | Focused `pnpm test:integration <ordinary-file>`; `test:integration:adapters` covers matching `infrastructure/__tests__` files only |
| Module workflows or public APIs | `pnpm test:integration:workflow` |
| Auth, routing, session, upload, or full-stack persistence | `pnpm test:e2e:chromium` |
| Critical screens or layout-heavy UI | `pnpm test:e2e:visual` |
| Framework config, env loading, production runtime, dependencies | `pnpm build` |
| Merge-level confidence | `pnpm verify` |

Mutation testing is intentionally slower. Use scoped commands during deep work, for example `pnpm test:mutation:auth:fast`, and run `pnpm test:mutation:critical` before high-risk merges or through the manually dispatched mutation-testing workflow.

## Review Checklist

- The test layer matches the risk: pure logic is not only covered by E2E, and browser-only behavior is not only covered by unit tests.
- Assertions prove observable behavior, not implementation details.
- Public workflow integration tests call only public module APIs.
- Adapter integration tests assert durable state or provider contract effects.
- Property tests have bounded, reproducible generators and clear invariant names.
- New architecture or security regressions have guardrails through depcruise, Semgrep, or `check:test-layering` where practical.

### Focused detection write recovery

`pnpm test:integration tests/integration/composition/image-detection-intent.integration.test.ts` checks rollback, retries, and commit reconciliation through the local test database driver. To exercise PostgreSQL server-raised faults, set `RECOVERY_TEST_DATABASE_URL` to a disposable direct loopback PostgreSQL database whose name starts with `selective_designer_recovery_test_`, then run the same command. The suite applies migrations and truncates that database. The loopback connection must not tunnel to a remote database. The default socket emulator uses driver-shaped failures around real transaction rollbacks because repeated server error responses are not supported reliably by its protocol bridge.

## E2E server ownership

`pnpm e2e:webserver` loads `.env` then `.env.example` without replacing inherited settings, applies test labels and disabled email, and selects the disposable loopback binding. Blank `E2E_DATABASE_URL` values use the default; malformed and foreign targets fail with a credential-free diagnostic. The launcher owns the in-memory PGlite database, socket listener, and Vite development server. Validation, migrations, seed, and build-info generation reuse their existing Node entrypoints in finite child processes. No nested package-manager command owns a server.

SIGINT/SIGTERM during startup or after readiness stops the active setup child and closes both listeners within ten seconds. Vite's awaited final-close hook includes database cleanup; a Vite restart preserves the database. Lifecycle regressions retain freshly verified launcher-PID-only signals to prove ownership and add verified process-group signals to reproduce terminal Ctrl+C during setup. Group tests supplement the PID-only cases; they do not replace them. Normal Playwright group teardown remains supported.

Signal-triggered shutdown and CLI startup failure flush diagnostics and exit explicitly, including when a plugin retains a referenced handle after closing. One referenced ten-second terminal deadline covers cleanup and final output and never restarts on repeated signals. The CLI starts this budget for a provisional child interrupt without declaring failure; cancellation classification can still reconcile before settlement. At nine seconds the launcher warns that shutdown is still pending and attempts to flush; that warning does not itself change exit status. At ten seconds it force-exits with failure. Output delivery at the hard stop is best effort when the consumer is blocked. Successful deliberate cancellation uses status zero unless a nonzero status was already set; genuine startup failure, cleanup failure, or terminal timeout uses status one. A setup child's signal outcome stays provisional until final reconciliation: it counts as deliberate cancellation only when it matches a signal received by the launcher or successfully requested through the retained child handle before settlement. Both event orders are supported; settled failures stay historical. Nonzero setup exits and unrelated acquisition errors remain failures even if a signal races them. Active startup operations settle and record their outcomes before Vite's own SIGTERM exit can finish; hooks never await the outer startup promise.

Programmatic `close()` starts cleanup once and caches a ten-second bounded result. It rejects on failure or timeout without exiting or changing its caller's exit status. Work still pending at timeout remains observed and is not restarted; late completion cannot rewrite the cached result. Startup failures remain the primary diagnostic when cleanup also fails; cleanup failures are reported separately and make cancellation fail. Post-close IPC ping/pong verifies that callers remain responsive after successful, failed, and timed-out close attempts. Signal handlers remain installed through terminal finalization, including the final output flush. Reusable cleanup removes them only after both startup and the underlying cleanup work settle, even when the bounded public promise has already timed out. A subsequent signal joins that pending work under its terminal deadline without restarting cleanup; the prior failure remains unsuccessful. One shared error registry reports each original diagnostic once, while a later terminal path can still mark an already-reported failure as unsuccessful.

Vite ownership uses an E2E-only config bridge that statically imports the selected config and registers before application hooks, including hooks with both pre priorities. It refreshes native default config discovery (`js`, `mjs`, `ts`, `cjs`, `mts`, `cts`, in that order) before each serialized native restart, including no-config startup, later additions, precedence changes and deletion fallback. Explicit config paths stay fixed; explicit `false` disables discovery. The persistent bridge uses static imports so selected config and imported dependencies retain native watching. The generated bridge uses one canonical real path for loading, writing, unwatching and removal; the allocated directory is already owned if canonicalization fails, with removal errors retained after the original failure. Only that bridge is unwatched, avoiding self-triggered restarts without changing disabled watchers or user ignore settings. Unselected default-file additions require an explicit restart, matching native Vite behavior. Raw plugin callbacks retain their order, metadata and receiver. Immutable lifecycle properties use writable plugin facades: direct facades and descriptor-forwarding wrapper aliases use the source receiver for source-plugin getters and setters, including accessors backed by private fields. Ordinary method values and Vite callback contexts remain unchanged. Genuinely derived objects and explicit foreign receivers retain their actual receiver for source accessors and local overlays. Deleting a local override reveals the live source again; deleting a source-owned property without a local override returns false. Deleting an absent or inherited-only property remains a successful no-op. Failed receiver-descriptor inspection means the receiver is not recognized as an alias; ordinary data reads remain possible, while actual accessor and receiver-operation failures still propagate. Lifecycle instrumentation is the explicit exception: its overrides belong to the facade and remain shared across aliases and derived objects. A private own marker identifies forwarding aliases without following prototypes; bookkeeping is hidden from enumeration and protected against deletion or redefinition. Custom proxy traps retain normal control, including rejecting writes; proxies that conceal or fabricate descriptors have no transparency guarantee. New and permitted shadow properties belong to the actual receiver and respect its descriptors and extensibility. This preserves receiver-based state, not arbitrary state captured by plugin closures; data properties, absent properties and getter-only accessors accept local overrides, while untouched properties and source accessors stay live. Explicit local descriptors and lifecycle instrumentation retain precedence; immutable source objects are not rewritten; synchronous close-hook throws become promise rejections so independent hooks still start. Late-installed hooks remain observable. Hook discovery does not populate Vite's sorted-hook caches early; resolved hook lookup methods and private Vite lifecycle methods are never patched.

The coordinator retains one native restart and its reconciliation work until completion, even after a caller times out. The five-second retirement deadline covers exposed teardown work and sibling close hooks; replacement creation and listening retain Vite's native timing. The public `closeServer` phase marks completion of native teardown attempts, not proof that every internal closer succeeded. Replacement adoption is reconciled before any saved callback can be used to close an abandoned generation. Public server and environment listening checkpoints confirm adoption before delegating, covering ordinary and middleware servers without charging listening to retirement. Completed predecessors release owner-held config, callback and resource records even while listening remains pending. Old proxy aliases must never close an adopted replacement. Candidate cleanup still runs application hooks; fixture final-shutdown labels, waits and failures require operation-scoped shutdown intent for the active instance. Joining cached retirement never changes its intent when a signal arrives.

Restart requests serialize behind pending cleanup. Each coalesced batch has its own caller results and underlying owned completion: successful A remains successful if later B fails. Requests coalesce before execution; later requests enter the next batch. Startup and incoming-generation lifecycle requests receive immediate acceptance to avoid waiting on themselves. Requests retain their originating generation until adoption; abandoned contributions and their force flags are discarded without removing independent active-owner requests. External callers await their own batch. A batch waiting behind cleanup has no additional queue timer. Cleanup attempts own immutable five-second absolute deadlines, separate from generation resource scopes. Predecessor teardown and candidate/orphan disposal discovered after native listening have separate budgets when their actual work starts; joining pending work and scope release never renew its deadline. Replacement creation and listening do not consume a later cleanup attempt’s budget. A timeout logs once without marking terminal failure, leaves that batch's result historical, and keeps underlying work and queued requests owned. New callers do not inherit the old timeout. Successful late reconciliation resumes eligible queued work. Genuine completed failure rejects pending requests with the original failure and clears their options; later explicit batches remain possible. Shutdown cancels accepted requests that never reach native invocation, including work paused in configuration refresh, without treating cancellation as cleanup failure. A genuine refresh rejection remains a failure. External cancellation remains rejected; the public Vite logger decorator suppresses only exact owner-created cancellation strings or object identities during shutdown. Non-string runtime inputs pass through unchanged. Explicit local logger definitions and spies use normal override behavior; spy restoration resumes live source lookup. Ordinary state assignments still update the application logger and forwarded methods retain its receiver. Started operations retain their outcomes; calls arriving after shutdown or through retired callbacks resolve quietly. Queue ownership is released synchronously when the queue drains. Settled historical cleanup errors remain visible at final shutdown without poisoning later successful restart results.

Observation of an active scope drains only already-launched work: prior watcher closure does not authorize closing the retained server’s environments or WebSocket, declaring disposal complete, or releasing that scope. Native teardown, confirmed retirement, abandoned/orphan disposal and final shutdown explicitly authorize disposal. Released configurations stay terminal through every observer entry point and saved factory callback. Unchanged instrumentation failures are recorded once while later callback/descriptor changes remain discoverable. Throwing getters are probed on later preparation calls, with one retained diagnostic per unchanged read-failure episode; recovery without a descriptor change remains discoverable. Every selected sibling hook and captured public close promise remains observed, including when Vite discards native errors or rejects its outer close early. Preparation failures never suppress the teardown action or hide its primary error. Registration commits retained cleanup callbacks before observation. Owner-initiated resource retirement reserves one shared promise before yielding, so concurrent dependent parts cannot schedule the outer wrapper repeatedly. Public captured-closer delegation remains separate from that promise to avoid self-waits. Cached retirement returns distinct failure outcomes rather than swallowing them; parent failure cannot prevent sibling drainage. Direct failed-initialization environment close rejects with the sole original failure, or an aggregate ordered by environment close then hot/optimizer/bundled parts, while final settlement retains those failures without retrying. Settlement expands only observer-created aggregates through immutable private constituent snapshots, deduplicating original values in first-occurrence order. Direct close still retains its native-first aggregate and cause; foreign plugin aggregates stay atomic with their original identity and context. Cached and released settlement retain the same normalized outcomes, including nested owned wrappers whose public error arrays were later mutated. An in-flight outer resource close must settle before the observer considers an uncalled native fallback, preserving pre-delegation flush ordering. A rejecting wrapper can still permit the native closer's first attempt. Cleanup operations are not automatically retried: native watcher close can cache rejection or return without rerunning failed work, and retrying an outer wrapper can replay application effects. Each completed generation and final-settlement scope releases its owner-held graph references and callback/resource records immediately after confirmed retirement and its own cleanup settlement, independently of stuck siblings and without another restart. Pending continuations and observer context retain lightweight tokens rather than obsolete graphs; failure values remain separate and active or pending work stays owned. A timeout alone does not fail final shutdown if owned cleanup succeeds within shutdown’s own deadline. Settled historical failures do not prevent removal of the config bridge. Final closure joins ownership work before releasing the shared database once.

The environment factory adapter captures the WebSocket context and watcher before full server construction. All launched factory/init peers settle before orphan cleanup. A rejected factory uses a minimal failure carrier without adding a named environment. Failed initialization preserves its original cause. Every environment, including the default runnable SSR environment, gets one attempt through its existing close method before its dependent hot, optimizer and bundled-development resources drain. The factory-context WebSocket is independently retired even when it is also the client hot channel; a pending environment close cannot block it. Failed-initialization part cleanup never waits recursively on its own parent retirement. The selected conservative policy retains a native missing-plugin-container rejection as a secondary cleanup diagnostic rather than bypassing custom cleanup or intercepting the getter. Subclass code after a rejecting parent close and hidden runner/container disposal cannot be guaranteed through these public APIs. Custom cleanup failures remain visible and native closers are not retried. These guarantees cover exposed resources and returned promises, not inaccessible plugin containers, hidden plugin work or private Chokidar closer completion. A successful exposed promise is not proof of every internal cleanup action. Regressions exercise early plugin/factory failure, read-only and late hooks, timed-out native work, batch-specific results, generation eligibility, shutdown cancellation, independent scope release, watcher and close-hook retirement, retained abandoned callbacks and immediate port reuse. Scoped AST/Semgrep guardrails keep literal lifecycle replacements in the coordinator, observer or explicit fault fixtures; the deterministic races prove sequencing and outcomes.

Ordinary launcher lifecycle tests use explicit in-process port overrides and OS-assigned loopback listeners. They report actual database and HTTP endpoints through fixture IPC, use their own occupied-port sentinels, and reuse the same assigned endpoints to prove immediate restart. They do not require ports 3000 or 54329 to be free. Environment-supplied Playwright database targets retain the strict disposable-endpoint validation above.

Lifecycle fixture bootstrap announces IPC readiness and waits for parent authorization before importing the launcher or acquiring databases, Vite servers, or setup children. The parent retains a freshly validated process-group capability before sending authorization, within its original five-second launch budget, checking again after identity validation before sending authorization. Bootstrap timeout or disconnection acquires no resources.

Launcher process exit and stdio closure are separate observations under one absolute twelve-second wait budget. An inherited open pipe produces an explicit output-drain failure. Disposal and failed-launch recovery share one absolute three-second budget for inspection, signaling, exit, and drain confirmation. Before authorization, recovery may terminate only the retained direct-child handle: the bootstrap gate guarantees it has not started descendants. A bootstrap that never announces readiness fails with its own readiness timeout, including captured output, distinct from process-group inspection timeouts. Group signaling still requires fresh verification. After registration, any group inspection, identity, or signaling failure preserves the leader and capability without retrying that cleanup operation. No signal was sent, so that pass reports immediately instead of waiting for an exit. Killing the leader could destroy the only retained witness for children created since launch. A transient inspection failure can be retried using the same retained capability. If identity validation marks continuity lost and clears its witnesses, a later snapshot cannot reauthorize a still-live group; the safeguards are not relaxed.
