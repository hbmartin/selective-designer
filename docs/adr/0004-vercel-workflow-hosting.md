# Host on Vercel with Workflow SDK

Use Vercel with Workflow SDK for durable rendering tasks; current official documentation supports the app's TanStack Start/Nitro setup. This reduces service and worker setup compared with a separate managed runner or an always-running queue worker, while accepting Vercel-specific deployment and execution constraints. Keep recipes, model attempts, costs and history in application-owned records, and isolate Workflow calls behind infrastructure/composition so the scheduler can be replaced.

The Nitro workflow host initializes telemetry independently of SSR, and both entry points isolate user context per request. Terminal unresolved diagnostics use one acknowledged attempt per sink with a five-second limit. Failed preparation or delivery falls back to a sanitized console record. If logger configuration is invalid, diagnostic reporters write one configuration notice per process and send each terminal event only to the console. SSR still rejects invalid configuration and can report its startup failure to Sentry. The default production `error` threshold filters intermediate warnings. Warnings admitted by `LOGGER_LEVEL` use the separate best-effort batch exporter when OTel is configured. Workflows await terminal diagnostic delivery within the deadline. The default Nitro Node server and Vercel can retain upload diagnostics through the request's `waitUntil` while the response returns. If the hook is absent or registration fails, the upload writes the fallback to console immediately. Diagnostic delivery never changes workflow results or accounting dispatch.
