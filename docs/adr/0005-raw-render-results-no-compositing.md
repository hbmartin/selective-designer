# Keep render results raw; never composite them into the render source

Each render result is stored and shown exactly as the model returned it. We never paste generated pixels back into the render source inside a feathered mask, even though research recommended that technique ("paste-back" in Photoshop layers, InvokeAI and BrushNet) as the way to guarantee unchanged pixels outside an edit. The user chose raw results so every model's real behaviour stays visible and comparable, and to avoid compositing artefacts: seams, colour shifts at mask edges, and shadows or glow cut off at the mask boundary.

## Consequences

- The promise that "only what was asked changes" depends on the models. The browser-side checker shows a change warning, and the compare view (side-by-side, swipe and onion skin) lets the user inspect drift. Neither blocks, alters or reruns a result.
- Drift can build up over several rounds of continuing from render results. Rendering from the base image (ADR 0002) is the escape hatch.
- If the first user rejects the results because of drift, revisit this decision. Paste-back could be added as an optional view of a result without changing the stored raw result.

Each render attempt publishes at most one image. Attempt output objects use create-only writes, so replay and concurrent completion preserve the first stored bytes. Durably capture the provider's performed work before publication; delivery to the cost log is independent (ADR 0009). Commit the image, detection intent, render completion, and output-image link together; a replay can reuse that registration without another provider poll or copy. Publication checks the current attempt and provider request. Retrying a failed result explicitly starts another attempt with a distinct image identity. Historical images are not rewritten.

Checkpoint a provider's successful output before downloading URL output or publishing it. Recovery of the same attempt reads its checkpoint and any create-only object already in private storage before accessing the provider again. Persist byte-based output in private storage and keep only its reference in the checkpoint. The checkpoint and provider cost metadata stay server-only. Manual Retry atomically starts a fresh attempt and clears its recovery state; it may purchase a new result. A provider response lost before its durable workflow handoff can still lead to repeat charges. Accepted submissions and their database persistence use separate durable steps, so persistence retries reuse the same request. Journaled acceptance retries database persistence with durable 5, 10, 20, 40 and then 60-second backoff until the original 30-minute attempt deadline. It never resubmits to the provider. Exhaustion leaves the attempt owner-retryable without claiming provider failure; permanent identity or validation failures fail only the matching owned attempt immediately. Recovery never resets attempt time.

A dispatched render names its expected attempts. Each attempt binds to one workflow run before submission. Submission, provider-result checkpoints, completion, and failure use compare-and-set fences, so an older timeout or response cannot fail or complete a replacement. Duplicate dispatches do not independently submit the attempt. No existing render jobs need adoption during this cutover; obsolete render step signatures are not retained.

An owner can start a fresh attempt after failure or after a pending or submitted attempt has lasted 30 minutes. Attempt start is persisted before dispatch and resets only for a new attempt. The same eligibility rule governs the editor and atomic retry claim. A late original workflow may still return paid work, but cannot publish over the replacement. A workflow that never claimed ownership cannot fail the attempt. Unclaimed work remains pending and becomes owner-retryable after the existing 30-minute window; this avoids a failing duplicate closing healthy queued work. Existing rows receive a fresh 30-minute window when the attempt-start migration is applied. Its timestamp default is explicitly UTC so a database session timezone cannot shorten that window.

Capture successful output and its request-level accounting receipt in one transaction. Replay uses the canonical checkpoint; original provider identity and timestamps remain stable. Cost-log delivery failures leave independent receipts pending and do not block publication or retire otherwise usable output. Same-attempt completion is successful replay, not supersession. Future terminal writes retire the source URL atomically while retaining nonsecret metadata and object keys. Existing terminal URLs are not rewritten. Manual Retry clears the checkpoint and captures its old object key atomically. The Retry transaction also persists independent cleanup responsibility for the original result, attempt and exact deterministic object key. Cleanup survives scheduling failure, worker interruption and parent deletion. The replacement workflow starts rendering promptly and separately processes that record; a daily workflow and operator command redrive pending cleanup with fenced five-minute leases. Every deletion validates its namespace and original attempt and checks global image/checkpoint references; failed checks retain the file. Cleanup records do not pin objects. This is prospective recovery, not historical orphan cleanup. Independent accounting receipts survive Retry and deletion.

A losing execution can discard an output only after confirmed creation and confirmed loss, including a canonical checkpoint choosing another key. Global image and checkpoint reference checks protect published and retained outputs; uncertain writes or checks retain the file. Storage metadata checks avoid full downloads merely to establish existence. Publication still validates the stored bytes and gives recognized image signatures precedence over MIME metadata.

No pre-receipt render jobs need recovery in this release. Active submissions and checkpoints require explicit request-level accounting; existing completed registrations and historical accounting remain unchanged.

Journaled acceptance always receives one persistence attempt, including a provider response received after the original deadline. A successful fenced save may continue the current render; only further transient recovery is bounded by that deadline. Invalid deadline metadata cannot block a valid initial receipt/submission save. If that save succeeds, the current fenced attempt continues normally; only further persistence retries need a valid original deadline. After a failed save, malformed journal metadata is recovered only from the matching owned attempt’s persisted start time, preserving its original 30-minute deadline. A reconciled matching save continues polling even after the cutoff. Unavailable reconciliation, unavailable original time, or exhausted recovery retains unresolved work rather than failing a possibly committed submission. Capture confirmation survives submission-write failures and controls delivery dispatch. At exhaustion, unconfirmed accounting can remain only in the journal; this release deliberately adds no post-deadline capture workflow. Recovery failure presentation uses an application reason, while server diagnostics retain the detailed code.

Unsafe cleanup targets cannot block a fresh manual Retry. The same transaction records sanitized, fingerprinted blocked evidence and retains the object; real bookkeeping failures still roll back Retry. Invalid queued targets are quarantined atomically before storage access. Queue eligibility, leases and sweep time use the database clock, and pagination follows the indexed time/key tuple. Completed deduplication records and blocked evidence are retained without pruning. The registry retains an exact, server-only bucket-relative locator only when it passes focused non-normalizing safety validation; unsafe evidence remains fingerprint-only, with no URLs or provider payloads. Ordinary diagnostics never disclose locators. Explicit operator inspection may display a safe locator, and explicit requeue may correct result/attempt identity only when the stored key exactly matches that deterministic render target. Requeue only creates normal cleanup work, preserving global-reference safeguards. Its append-only audit and queue transition commit together. An explicit repair can reopen a previously retained job and preserves its earlier completion evidence; ordinary sweeps and enqueue never reopen completed jobs. Active leases are not stolen, deleted tombstones stay closed, and historical fingerprint-only records are not reconstructed. No historical scan or repair UI is introduced.

Cleanup claims require an explicit root transaction runner; missing metadata never implies transaction ownership. Eligibility and leases use database time, while tuple cursors use the same UTC millisecond encoding as stored timestamps. Nonempty pages require an advancing cursor. Reports distinguish execution-local work from cumulative blocked evidence; retained registry and recovery records are not pruned.

Operator repair and queue claims also prove attempt eligibility: older attempts, missing parents and terminal current attempts are eligible; active and future attempts are not. A queued active target is quarantined for explicit later repair before any reference or storage operation. Terminal eligibility never overrides global references. Result locks precede queue locks, matching manual Retry’s lock order.

Blocked evidence is historical; `blockedTotal` never implies an actionable backlog. `blockedOutstanding` counts evidence with no successful audited repair handoff or acknowledgment. An operator may acknowledge blocked evidence as accepted retention; this performs no deletion and preserves a static reason in append-only recovery history. Repair handoff clears intervention responsibility immediately, leaving normal cleanup to finish independently. CLI paging reaches older evidence, and an explicit request ID safely replays uncertain repair or acknowledgment commands across process invocations.

Reconcile a journaled submission from one row snapshot, comparing the complete saved identity. This avoids misclassifying our own concurrently committed save as supersession. The repository reports matching submission evidence without interpreting accounting state. The application confirms capture from that evidence because the only production submission write follows durable receipt capture. Read-only reconciliation retries transient failures through the pinned SDK: three attempts with five-second waits. A confirmed save may resume polling after the cutoff; only further submission writes require the original deadline to remain open. The pinned SDK normally suspends or resolves durable waits. Defensive handling of an interrupted wait records safe diagnostics and reconciles uncertain submission writes before returning unresolved: a matching saved request continues polling, while an unavailable read retains existing capture progress and the original cutoff.

Operators can acknowledge deliberate retention of any blocked target without changing a render, authorizing deletion, or accessing storage. Missing locators retain the original static reason; other retention uses `operator_retained`. One canonical acknowledgment per fingerprint is protected by fingerprint serialization. Additional request identities are durable aliases, preserving idempotent replay and cross-action conflicts without duplicate acknowledgment events. Existing historical duplicates remain unchanged and the earliest is canonical. New acknowledgment cannot cancel a repair handoff, while a later explicit repair can hand acknowledged evidence to normal cleanup; handoff takes precedence in intervention reporting. Evidence, audit events and aliases remain retained. Apply additive migration 0020 before deployment; it performs no historical backfill.

Intervention projections correlate acknowledgment and repair evidence to each blocked fingerprint independently. Alias replay validates its target and resolves the earliest historical acknowledgment with at most two reads; existing advisory locks and runtime checks continue to protect replay identity. This focused correction leaves the alias schema, migration 0020 and historical evidence unchanged.
