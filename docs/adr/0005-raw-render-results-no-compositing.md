# Keep render results raw; never composite them into the render source

Each render result is stored and shown exactly as the model returned it. We never paste generated pixels back into the render source inside a feathered mask, even though research recommended that technique ("paste-back" in Photoshop layers, InvokeAI and BrushNet) as the way to guarantee unchanged pixels outside an edit. The user chose raw results so every model's real behaviour stays visible and comparable, and to avoid compositing artefacts: seams, colour shifts at mask edges, and shadows or glow cut off at the mask boundary.

## Consequences

- The promise that "only what was asked changes" depends on the models. The browser-side checker shows a change warning, and the compare view (side-by-side, swipe and onion skin) lets the user inspect drift. Neither blocks, alters or reruns a result.
- Drift can build up over several rounds of continuing from render results. Rendering from the base image (ADR 0002) is the escape hatch.
- If the first user rejects the results because of drift, revisit this decision. Paste-back could be added as an optional view of a result without changing the stored raw result.

Each render attempt publishes at most one image. Attempt output objects use create-only writes, so replay and concurrent completion preserve the first stored bytes. Record the provider's performed work before publication. Commit the image, detection intent, render completion, and output-image link together; a replay can reuse that registration without another provider poll or copy. Publication checks the current attempt and provider request. Retrying a failed result explicitly starts another attempt with a distinct image identity. Historical images are not rewritten.

Checkpoint a provider's successful output before downloading URL output or publishing it. Recovery of the same attempt reads its checkpoint and any create-only object already in private storage before accessing the provider again. Persist byte-based output in private storage and keep only its reference in the checkpoint. The checkpoint and provider cost metadata stay server-only. Manual Retry atomically starts a fresh attempt and clears its recovery state; it may purchase a new result. A provider response lost before its checkpoint is durable can still lead to repeat charges.

A dispatched render names its expected attempts. Each attempt binds to one workflow run before submission. Submission, provider-result checkpoints, completion, and failure use compare-and-set fences, so an older timeout or response cannot fail or complete a replacement. Duplicate dispatches do not independently submit the attempt. No existing render jobs need adoption during this cutover; obsolete render step signatures are not retained.

An owner can start a fresh attempt after failure or after a pending or submitted attempt has lasted 30 minutes. Attempt start is persisted before dispatch and resets only for a new attempt. The same eligibility rule governs the editor and atomic retry claim. A late original workflow may still return paid work, but cannot publish over the replacement. Failure before workflow ownership is claimed may close only the matching unowned, unsubmitted pending attempt. Existing rows receive a fresh 30-minute window when the attempt-start migration is applied. Its timestamp default is explicitly UTC so a database session timezone cannot shorten that window.

Checkpoint successful output before requiring the idempotent cost log. Replay records accounting from the canonical checkpoint before publication; its original provider identity and timestamps remain stable. Same-attempt completion is successful replay, not supersession. Future terminal writes retire the source URL atomically while retaining nonsecret metadata and object keys. Existing terminal URLs are not rewritten. Manual Retry clears the checkpoint.

A losing execution can discard an output only after confirmed creation and confirmed loss, including a canonical checkpoint choosing another key. Global image and checkpoint reference checks protect published and retained outputs; uncertain writes or checks retain the file. Storage metadata checks avoid full downloads merely to establish existence. Publication still validates the stored bytes and gives recognized image signatures precedence over MIME metadata.
